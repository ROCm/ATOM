## Caveats for C (read before spending GPU time)
1. C carries THREE needs_gsm8k_gate items: SP prefill (not bit-identical to TP4), AK_WIDE (AK vs q8 route, ~1 ulp),
   plus B's mono cap 8 / draft AR (B passed thin: 0.9625). Gate C before counting its AgentX numbers.
2. SP prefill has never served live multi-request steps on int5 (only prefill_bench, 1 request); first contact is the
   gate/point. The SP pull hand-off buffers are built at the first SP forward (the warm-up dummy prefill of 2x16384
   tokens takes SP, so they should land inside the profiled peak): compare KV blocks / "KV cache" lines with B's log.
   o_proj_full (+2.9 GB/rank) is a model weight (constructed in __init__, loaded with o_proj) and is inside the budget.
3. Expected KV pool: ~157.5 GB (B at 0.85) - 14.4 (0.80) - 2.9 (o_proj_full) ~= 140 GB/rank (-11%); B peaked at 33.6%
   of 157 GB (53 GB), so no capacity loss is expected at c32. Startup compiles the eager SP prefill kernels and
   the AK attention variants at 136-256 rows into flydsl_armC: first start is longer.
4. ITL-risk PF cost constants (31.6 ms fixed + 18.65 ms/1K tokens) were fitted to TP prefill steps; SP steps >= 2K are
   17-26% cheaper, so the hold over-estimates stalls (conservative: more holding than intended). Not retuned (no data).
5. AK_WIDE covers k7 (ql 8) only; k3 untouched.
