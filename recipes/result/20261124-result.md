## Findings

- Base changed: this session's image `rocm/fw-bringup-mlperf:gfx1250-atom-ci455-20261124` is built on the ROCm 10.2.0 base `amddcgpuce/rocm-rel:ub24-dcgpu-rk-10.2.0-pyt2.14.0-rocmtri3.9-24d5394c-atomsrc-gfx1250-b1123` (torch 2.14.0+rocm10.2.0, Triton 3.9.0+amd.rocm10.2.0, FlyDSL 0.5.3, MORI 1.2.6) instead of the previous 455-CI image (ROCm 10.1). Only `atom` and `amd-aiter` differ from that base. The tag already carried the 455-CI labels when this session started (pushed 15:19 BJ), so it was used as is (guide §2.2).
- The 10.2 base activates its gfx1250 venv only in its entrypoint, so `docker exec` does not see ATOM, and it has no `lm_eval`. The servers ran with `-e PATH=/root/venv/atom-venv-gfx1250/bin:<image PATH> -e VIRTUAL_ENV=... -e GPU_ARCHS=gfx1250 ...` (what the entrypoint sets), and GSM8K ran in a sidecar of the 20261121 image that shares the server container's PID namespace. Server and GSM8K commands are the recipe's (455-CI `76df6ffd`).
- Trays: e15-05 and e15-08 for the single-node models (e15-06 and e15-07 were in use); Kimi-K3 on e15-06 + e15-07. GSM8K of the single-node models is in line with the earlier sessions.
- Kimi-K3: the first attempt, on e15-05 + e15-08, took down both trays. One minute after the servers launched, e15-05 logged `Failed to initialize PyNcclCommunicator for group tp:0. Exception: NCCL error: unhandled cuda error`, and both trays reset; the next boot reports `Previous system reset reason [0x88000000]: an uncorrected error caused a data fabric sync flood event` on both. e15-05 had also logged about 156k corrected `[Hardware Error]` machine checks (CPU bank 57) and GPU ACA events since 2026-11-23. The same image on e15-06 + e15-07 (with `NCCL_DEBUG=INFO`) initialised RCCL normally and gave GSM8K 0.9704, so the reset points at the e15-05/e15-08 pair rather than the image. [attempt 1 log](../455-CI/runs/20261124/kimi-k3/attempt1_0508/error.log)
